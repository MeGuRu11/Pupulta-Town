# Локальная среда Docker и Supabase

## Задача

Поднять воспроизводимую локальную среду для разработки Pupulta Town на Windows с WSL 2 и проверить PR 3 на настоящем контейнере Supabase PostgreSQL.

До изменения конфигурации наблюдались два независимых сбоя:

- Docker Desktop, запущенный напрямую из оболочки агента Codex, завершался на `Secrets Engine` с ошибкой доступа к `engine.sock`. После запуска через Windows Explorer движок ответил на `docker info`. Совпадающий сценарий описан в пользовательском [issue OpenAI Codex #52698](https://github.com/openai/codex/issues/52698); это рабочий обход для проверенной установки, а не подтверждённая причина всех подобных ошибок.
- Контейнер Vector перезапускался: источник `docker_logs` не мог подключиться к `host.docker.internal:2375`. В [Windows-ветке Supabase CLI 3.0.0](https://github.com/supabase/cli/blob/v3.0.0/apps/cli/src/commands/start/services/vector.service.ts) для Docker named pipe выбирается именно этот TCP-адрес.

## Изменения

1. `supabase/config.toml`: явно отключить необязательную локальную аналитику. Использовать документированный `analytics.enabled = false`, чтобы обычный запуск не создавал проблемный сборщик логов Vector. Docker API по TCP 2375 для этого не нужен.
2. `docs/local-development.md`: описать версии инструментов, запуск, остановку с сохранением данных, применение миграций, проверку базы и особенности Windows/Codex. Отдельно обозначить пример путей переносимых инструментов на текущем ПК.
3. Проверить фактические адреса опубликованных портов. Опция bridge-сети `host_binding_ipv4=127.0.0.1` на проверенной установке не дала локальную привязку: контейнер показывал `0.0.0.0` и `::`. Настройку Docker Desktop `Default port binding mode` требуется применить и проверить при новом создании контейнеров.
4. `README.md`: добавить ссылку на инструкцию локальной разработки.

## Проверка результата

- Docker: сервер отвечает на `docker info`; обычный запуск Supabase завершается без `--ignore-health-check`.
- Контейнеры включённых сервисов запущены и проходят предусмотренные healthcheck. После отключения аналитики Vector и Logflare не нужны для локального приложения.
- API и Studio доступны по HTTP; опубликованные порты проверены в Docker и на Windows. Одной записи в конфигурации недостаточно, чтобы считать привязку к localhost подтверждённой.
- `pnpm test:db`: ожидаются все 183 существующие проверки pgTAP — 26 примеров сетки, 32 проверки правил города и 125 проверок городов/задач. Новые тесты для документирования среды не добавляются.
- `pnpm verify`: общие проверки проекта проходят после изменения конфигурации и документации.
- Проверить `git diff` на соответствие задаче и отсутствие секретов. Фактические результаты запусков фиксируются после выполнения проверок.

Схема базы и прикладная логика этим изменением не меняются. Настройка локального Docker не требует подключения к hosted-проекту Supabase.

## Фактический результат, 8 ноября 2026

- Docker Desktop 4.97.0, Engine 29.9.2, Linux, WSL 2. Запуск через Explorer и последующий обычный перезапуск сработали.
- В реальном пользовательском `settings-store.json` установлен документированный `portBindingBehavior = default-local-port-binding`. Исходный файл сохранён рядом как `settings-store.json.pupulta-backup-20261108-130519`. Это настройка Docker Desktop для новых контейнеров, а не только для проекта.
- После `supabase stop` с сохранением данных выполнен `supabase start --network-id supabase_network_pupulta-town`. CLI завершился с кодом 0 без пропуска healthcheck.
- Запущены 10 контейнеров проекта. Восемь имеют `healthy`; у REST и Edge Runtime healthcheck не предусмотрен. При итоговой проверке все имели `RestartCount = 0`.
- Docker inspect показывает только `127.0.0.1` и `::1` для опубликованных портов 54321, 54322, 54323 и 54324. Дополнительный контейнер с публикацией без явного IP также получил loopback-привязки и был удалён после проверки. `Get-NetTCPConnection` не показал слушателей этих портов; `netstat` показал локальные соединения. Отдельная проверка достижимости с другого компьютера не проводилась.
- Studio, Mailpit, Auth health и REST schema вернули HTTP 200. PostgreSQL ответил `accepting connections`; обе миграции присутствуют в локальной базе.
- `pnpm test:db` после перезапуска: 183 проверки в трёх файлах, `Result: PASS`.
- `pnpm verify`: typecheck, lint, 91 тест Vitest и проверка ассетов прошли.
- `pnpm test:e2e`: 1 браузерный тест прошёл с существующим Chromium в явном `PLAYWRIGHT_BROWSERS_PATH`. Первый запуск без переменной не нашёл браузер; повторная установка не понадобилась.
- `git diff --check` прошёл. Данные подключения и ключи в документацию не включены.
