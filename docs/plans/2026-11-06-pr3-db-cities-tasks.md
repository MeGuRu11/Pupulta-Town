# PR 3 первого среза — города, задачи и права в Supabase

## Что меняем

Добавляем локальный Supabase и шесть таблиц из плана среза. Командные записи изменяются через функции создания города, входа по приглашению, создания задачи и смены статуса. Срок задачи — дата. Порча вычисляется по UTC+3. Права чтения проверяются RLS, а ключ приглашения доступен руководителю через отдельную функцию.

Размещаем задачу атомарно с назначениями и объектом. Ищем место по расширяющимся квадратам кварталов. Слот членства ограничен диапазоном 1–20, а уникальность слота защищает лимит при конкуренции. Геометрию защищают проверка границ квартала и ограничение пересечений в самой базе.

## Файлы

- `supabase/config.toml`, SQL-миграции и тесты в `supabase/tests/`.
- Проверка совпадения примеров сетки TypeScript и SQL.
- Команда `pnpm test:db` и краткий контракт вызовов и полей для будущего трекера.

## Проверки

- Сначала pgTAP на аутентификацию, изоляцию городов, роли, приглашения, лимит, целостность назначений, размещение и обновление статуса.
- Одинаковые примеры сетки и следов в Vitest и pgTAP. Проверка границы московского дня, ступеней и закрытия задачи.
- Чистый локальный запуск миграций, `pnpm test:db`, `pnpm verify` и CI.

## Контракт для трекера

| Вызов | Результат |
| --- | --- |
| `create_city(p_name)` | ID города. Создатель становится руководителем. |
| `get_city_invite(p_city_id)` | Токен приглашения. Доступен руководителю. |
| `join_city(p_invite_token)` | ID города. Новый участник получает роль исполнителя. Повторный вход возвращает тот же ID и сохраняет роль. |
| `create_team_task(p_city_id, p_title, p_size, p_due_on, p_assignee_ids, p_description)` | ID задачи. Задача, назначения и фундамент создаются в одной транзакции. Список исполнителей и описание можно опустить. |
| `set_task_status(p_task_id, p_status)` | Обновляет задачу и стадию объекта. Допустимые статусы — `todo`, `in_progress`, `done`. |

Все вызовы предназначены для аутентифицированного пользователя. Назначить можно руководителя или исполнителя своего города. Если список пуст, задача остаётся без назначения. Гость читает задачи города, если у него есть членство с этой ролью. Создание гостевых приглашений относится к отдельному пользовательскому сценарию.

Для списка городов запрашивай поля `id,name,seed,created_by,created_at`. Колонка приглашения закрыта для прямого чтения. В профиль можно записать только собственные `display_name` и `avatar`. Остальные командные записи меняются через функции.

`due_on` передаётся в формате `YYYY-MM-DD`. При первом закрытии база записывает `closed_at`, повторное закрытие сохраняет его, а открытие задачи снова очищает. Стадия объекта следует статусу: фундамент, стройка, готово. Ступень порчи вычисляется отдельно. Для будущей подписки на изменения в публикацию Realtime включены `team_tasks` и `city_objects`.

Координаты `cell_x` и `cell_z` обозначают начальную клетку основания. В пустом городе первый объект ставится в `(4, 4)`. Дальше база перебирает кварталы расширяющимися квадратами. Внутри квартала проверяется вся площадь S или M. Начальный поворот равен нулю.

## Локальный запуск

Из корня репозитория с работающим Docker и Supabase CLI 3.0.0 выполните:

```sh
supabase start
pnpm test:db
```

Если стек уже запущен до добавления миграций, примените их командой `supabase migration up --local` и повторите тесты. `pnpm test:db` проверяет актуальность SQL-примеров сетки и запускает pgTAP на локальной базе.
