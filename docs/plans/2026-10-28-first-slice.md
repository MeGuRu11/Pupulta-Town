# План первого вертикального среза

Дата: 2026-10-28. Статус: черновик, ждёт решения владельца по порядку работ (раздел «Порядок»).

Метки уверенности: \[Certain\] проверено, \[Likely\] сильный вывод, \[Guessing\] допущение, которое надо подтвердить.

## Цель среза

Доказать основной цикл от входа до здания на тонком куске каждого слоя: база, права, реальное время, симуляция, 3D-сцена, тесты, CI.

Срез готов, когда на локальной машине проходит такой сценарий:

1. Аня регистрируется, создаёт город и становится в нём руководителем.
2. Аня отправляет ссылку-приглашение. Борис входит по ней и становится исполнителем.
3. Аня создаёт задачу размера S или M со сроком и назначает её Борису.
4. У обоих в городе появляется фундамент на свободной клетке.
5. Борис берёт задачу в работу: фундамент становится стройкой. Закрывает: объект достроен. Аня видит каждое изменение меньше чем через 2 секунды без перезагрузки.
6. Если срок прошёл, а задача не закрыта, объект показывает ступень порчи. Закрытие задачи порчу убирает.
7. По улицам ходят жители. При одном seed города и одном времени картина одинаковая.

Всё это закрыто автотестами, `pnpm verify` и CI зелёные.

## Чего в срезе нет

Каждый пункт откладывается сознательно, а не забыт.

| Что | Почему не сейчас |
| --- | --- |
| Задачи размера L и подзадачи | нужен прототип модульного здания (прототип 3 из `architecture.md`), а моделей пока нет |
| Личный трекер и личная комната | отдельный поток с отдельными правами; второй срез |
| Монеты, журнал монет, декор | экономика без декора не проверяется; второй срез |
| Рейтинг, статуя, аналитика | нечего считать, пока нет монет и очков |
| Лента событий города | дешёвая, но не нужна для проверки цикла; второй срез |
| Аватары участников | их поведение зависит от присутствия в сети (Presence); второй срез |
| Модели из Blender | \[Certain\] в репозитории нет ни одного `.glb`, мудборд не готов. В срезе объекты и жители — простые фигуры (коробки, капсулы) |
| Развёртывание в интернет | срез живёт на локальном Supabase; облачный проект и хостинг выбираем после среза |
| Вход через GitHub или Google | почта и пароль проще в тестах Playwright \[Likely\]; соцвход добавляется без смены схемы |

## Что уже решено и на что опирается срез

- Решения `docs/decisions/0001`–`0004`: город = проект, задача = объект по размеру, роли, порча только от командных задач, стек.
- Инварианты из `AGENTS.md`: симуляция без `Math.random()` и `Date.now()`, права в RLS, ступень порчи не хранится, жизнь города не идёт по сети, до 20 участников.
- Модель данных из `architecture.md`, раздел «Модель данных». В срез входит её часть: `profiles`, `cities`, `city_members`, `team_tasks`, `task_assignees`, `city_objects`.

## Порядок

Спорное место. `architecture.md` говорит: сначала четыре прототипа, потом разработка, а прототип толпы решает, остаётся ли Three.js. Срез при этом трогает движок только в одном PR из шести (PR 5, сцена). Остальные пять от движка не зависят.

Рекомендация: PR 1–4, затем прототип толпы, затем PR 5–6. Так прототип толпы стоит прямо перед единственной частью, которую он может отменить, и не держит остальную работу. Прототип можно делать параллельно, например товарищем.

Прототипы 2 (Blender → сцена) и 3 (модульное здание) в срез не входят: им нужны настоящие модели.

## Pull request'ы

Каждый PR маленький и про одно. После каждого `pnpm verify` и CI зелёные.

### PR 1. `chore/monorepo` — каркас

- `package.json`, `pnpm-workspace.yaml`, `tsconfig` с `strict`.
- Пустые пакеты `apps/web`, `packages/sim`, `packages/shared`.
- ESLint с правилами-инвариантами для `packages/sim`: запрет импорта `three`, `react`, `@react-three/*`; запрет `Math.random` и `Date.now`; среда без DOM.
- Vitest, Playwright, скрипт `check:assets` (на пустой папке `assets/` проходит), скрипт `verify`.
- CI: \[Certain\] сейчас задачи `check` и `e2e` включаются по наличию `package.json`, `db` по наличию `supabase/config.toml`. В `e2e` нужно добавить `supabase start`, иначе сквозной тест из PR 6 не найдёт базу.

Тест, который докажет результат: файл в `packages/sim` с `Math.random()` роняет `pnpm lint`. Проверяем руками один раз и записываем в описание PR.

### PR 2. `feat/sim-core` — общие правила и симуляция

Чистый TypeScript, без базы и браузера. Подходит товарищу через Codex.

- `packages/shared`: типы (роль, размер, статус задачи), размер клетки сетки, `slotToCell(slot)` — номер места в городе превращается в клетку, `decayStage(dueAt, now, closedAt)` — ступень порчи.
- `packages/sim`: генератор случайных чисел от seed; жители ходят по улицам сетки; `simulate(seed, timeMs)` возвращает позиции.

Тесты Vitest:

- один seed и одно время дают одинаковые позиции, разные seed дают разные;
- `slotToCell` не выдаёт одну клетку двум номерам и не залезает на улицы;
- `decayStage`: до срока порчи нет; каждая граница ступеней; закрытая задача порчи не имеет.

### PR 3. `feat/db-cities-tasks` — база и права

- `supabase init`, миграция с шестью таблицами из раздела выше и RLS на каждой.
- Функции базы, через которые клиент меняет данные:
  - `create_city(name)` — создаёт город, seed и делает автора руководителем;
  - `join_city(invite_token)` — добавляет исполнителем, отказывает 21-му;
  - `create_team_task(...)` — только руководитель; база сама создаёт `city_objects` на следующем свободном месте (`slot`);
  - `set_task_status(task_id, status)` — назначенный исполнитель или руководитель.
- Клиент не пишет напрямую в `city_objects` и не меняет поля задачи, кроме как через функции. \[Likely\] Политиками RLS трудно разрешить исполнителю менять только статус, а функция делает это явно.

Тесты pgTAP, каждый на разрешённый и запрещённый случай:

- руководитель создаёт задачу; исполнитель и гость не могут;
- назначенный исполнитель меняет статус; чужой исполнитель и гость не могут;
- участник видит задачи своего города; посторонний не видит;
- клиент не может вставить или изменить `city_objects`;
- 20-й участник входит, 21-й получает отказ;
- нельзя создать задачу размера L (пока её нет в срезе).

### PR 4. `feat/web-tracker` — интерфейс трекера

- Вход по почте и паролю (Supabase Auth).
- Список городов, создание города, вход по ссылке-приглашению.
- Панель задач поверх места под сцену: список, создание (только у руководителя), смена статуса.
- Подписка на изменения задач через Supabase Realtime (Postgres Changes). \[Likely\] Эти изменения проходят через RLS, и чужой город подписчику не приходит; проверить по документации через Context7 до кода.
- Время для интерфейса и сцены берётся из одного источника. В тестовом режиме его и seed можно задать через параметры адреса, чтобы скриншоты были стабильными.

Тесты: Vitest на логику панели, вынесенную из компонентов; Playwright на вход и создание города.

### Прототип толпы (вне среза, перед PR 5)

Вопрос и критерий из `architecture.md`: 300 анимированных жителей и 50 машин, 60 кадров в секунду на встроенной графике. Код выбрасывается, в `main` попадает только итог в `docs/decisions/`.

\[Guessing\] Для анимированного жителя подойдёт тестовая модель из примеров three.js; её лицензию проверить до использования.

### PR 5. `feat/web-scene` — город в 3D

- Сцена React Three Fiber: земля, сетка улиц, общий ракурс с поворотом.
- Объект задачи — коробка: S на одну клетку, M на 2 × 2. Вид по статусу: фундамент, стройка, готово. Ступень порчи — цвет и значок поверх объекта.
- Жители — капсулы, позиции берутся из `packages/sim`.

Тест: скриншот Playwright с фиксированным seed и временем, сравнение с эталоном.

### PR 6. `test/e2e-two-players` — сценарий целиком

- Два контекста браузера: руководитель и исполнитель проходят сценарий из раздела «Цель среза».
- Проверка, что изменение у второго игрока появилось меньше чем за 2 секунды.
- Просроченная задача: время задаётся параметром, ступень порчи видна, после закрытия пропадает.

## Открытые вопросы

Значения по умолчанию стоят в коде как константы в `packages/shared`, их легко поменять.

| Вопрос | По умолчанию в срезе |
| --- | --- |
| Размер клетки сетки | 2 × 2 м, как в примере из `concept.md` \[Guessing\]. Менять дёшево только до первых моделей |
| Сколько дней просрочки до каждой ступени (грязь, граффити, дефект, ремонт, пожар) | 1, 3, 7, 14, 21 день \[Guessing\] |
| Может ли руководитель сам закрыть задачу исполнителя | да |
| Гость видит задачи города | да, только чтение |

## Что нужно на компьютере

Код среза пишется в Claude Code на компьютере владельца. \[Certain\] В облачном треде проекта не работают хуки и субагенты из репозитория, а Docker там не запущен, поэтому локальный Supabase и `pnpm test:db` не поднять.

- Node.js LTS и pnpm.
- Docker Desktop, запущенный.
- Supabase CLI.
- Claude Code, открытый в папке репозитория.

Для каждого PR в Claude Code достаточно сказать: «делаем PR N из `docs/plans/2026-10-28-first-slice.md`».
